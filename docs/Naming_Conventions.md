# Naming Conventions

This document defines the naming conventions for schemas, tables, views, columns, stored procedures and files in the data warehouse. Follow it for everything you add so the project stays consistent.

## General Principles

- **Case:** use `snake_case`: lowercase letters, with underscores (`_`) separating words.
- **Language:** use English for all names.
- **Reserved words:** do not use SQL reserved words as object names.

## Database and Schemas

| Object | Name | Notes |
|--------|------|-------|
| Database | `DataWarehouse` | The one exception to `snake_case`. |
| Schemas | `bronze`, `silver`, `gold` | One schema per layer. The scripts refer to these exact names. |

## Table Naming Conventions

### Bronze and Silver Rules

Bronze and Silver use the same rule, because Silver tables are the cleaned version of the matching Bronze tables.

- Every name starts with the **source system name**, followed by the **original table name** from that system, without renaming.
- Pattern: **`<sourcesystem>_<entity>`**
  - `<sourcesystem>`: name of the source system (`crm` or `erp`).
  - `<entity>`: the exact table name from the source system.

| Table | Source system | Source file |
|-------|---------------|-------------|
| `crm_cust_info` | CRM | `cust_info.csv` |
| `crm_prd_info` | CRM | `prd_info.csv` |
| `crm_sales_details` | CRM | `sales_details.csv` |
| `erp_loc_a101` | ERP | `loc_a101.csv` |
| `erp_cust_az12` | ERP | `cust_az12.csv` |
| `erp_px_cat_g1v2` | ERP | `px_cat_g1v2.csv` |

Example: `bronze.crm_cust_info` and `silver.crm_cust_info` hold the same entity at different quality levels.

### Gold Rules

Gold tables use meaningful, **business-aligned** names. They do not follow the source system names.

- Pattern: **`<category>_<entity>`**
  - `<category>`: the role of the table (see the glossary below).
  - `<entity>`: a descriptive, plural name aligned with the business domain (for example `customers`, `products`, `sales`).
- Examples:
  - `dim_customers`: dimension table for customer data.
  - `dim_products`: dimension table for product data.
  - `fact_sales`: fact table containing sales transactions.

#### Glossary of Category Patterns

| Pattern | Meaning | Example(s) |
|---------|---------|------------|
| `dim_` | Dimension table | `dim_customers`, `dim_products` |
| `fact_` | Fact table | `fact_sales` |
| `report_` | Report table or view (use only if the project adds report-level objects) | `report_customers`, `report_sales_monthly` |

## Column Naming Conventions

### Column Names by Layer

- **Bronze and Silver:** keep the **source column names** (for example `cst_firstname`, `prd_cost`), because the data comes straight from the source files.
- **Gold:** use clear, business-friendly names (for example `first_name`, `cost`).

### Surrogate Keys

- Every primary key in a dimension table is a surrogate key and must end with `_key`.
- Pattern: **`<entity>_key`**
  - `<entity>`: the **singular** name of the entity the key belongs to.
  - `_key`: suffix marking a surrogate key.
- Examples:
  - `customer_key` in `dim_customers`.
  - `product_key` in `dim_products`.

### Technical Columns

- Columns generated by the system (not coming from the source) must start with the prefix `dwh_`, followed by a descriptive name.
- Pattern: **`dwh_<column_name>`**
  - `dwh_`: prefix used only for system-generated metadata.
  - `<column_name>`: describes the column's purpose.
- Example: `dwh_load_date` stores the date the record was loaded.

> The current Bronze tables do not include technical columns. Add them following this convention when they are needed.

## Stored Procedures

- Procedures that load data must be named **`load_<layer>`**, and created in the schema of the layer they load.
  - `<layer>`: `bronze`, `silver` or `gold`.
- Examples:
  - `bronze.load_bronze`: loads the Bronze layer from the CSV files.
  - `silver.load_silver`: loads the Silver layer.

---

## File Names

- SQL scripts use `snake_case` and the `.sql` extension.
- Scripts that must run in a fixed order are prefixed with a two-digit number (for example `01_init_database.sql`, `02_ddl_bronze.sql`).
- Documentation files use `snake_case` with underscores (for example `naming_conventions.md`, `data_catalog.md`), so links between documents stay consistent.
